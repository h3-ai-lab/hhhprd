# PRD 类型提示词索引

先读取 [`prd-generation.md`](prd-generation.md)，再选择一个主类型提示词。所有类型共享“不写代码、不写验收、不输出写作检查、只保留一个原型地址”的规则。

正式 PRD 不设“待确认”或开放问题章节；尚未明确的事项应在生成 PRD 前完成决策。

任何新增功能、页面、按钮、字段组或数据列表，还必须读取 [`04-permission-audit.md`](04-permission-audit.md)，输出 RBAC 权限矩阵和权限数据变更清单。

用户要求“发布”或“上传 GitHub”时，完成后直接提交并发布，不再要求本地验证或二次确认；发布范围只包含当前任务相关改动。

生成原型时还必须读取 [`prototype-generation.md`](prototype-generation.md)，只展示上线后真实产品界面，不把 PRD 说明、流程叙事或原型提示画进产品页面。

## 路由原则

1. 先问“这个需求真正改变的是什么结果”，不是根据提到了哪个页面或按钮选类型。
2. 一份 PRD 只设一个主类型，决定文档主线和必须回答的问题。
3. 补充类型只用于确实存在的独立复杂问题，最多补充 1–2 个；权限与审计是例外，新增功能或数据列表时必须检查 RBAC。
4. 需求同时改变流程、字段、权限和指标时，仍按主问题组织，不把四套模板拼成四份文档。
5. 类型不确定时先写出主业务变化，再判断最接近的类型并标明补充类型。

## 类型目录

| 类型 | 提示词 | 主问题 |
|---|---|---|
| 业务流程 | [01-business-workflow.md](01-business-workflow.md) | 谁在什么触发下完成什么，业务对象如何流转 |
| 表单、字段与列表 | [02-form-field-list.md](02-form-field-list.md) | 用户维护什么数据，如何查找、筛选、排序、批量操作和导出 |
| 规则、状态与数据 | [03-rule-state-data.md](03-rule-state-data.md) | 什么条件下发生什么结果，状态和边界如何控制 |
| 权限与审计 | [04-permission-audit.md](04-permission-audit.md) | 谁能看、谁能改、数据范围多大、如何追溯 |

## 组合示例

| 需求 | 主类型 | 补充类型 |
|---|---|---|
| 新增“首位 CC”字段、筛选和导出 | 表单、字段与列表 | 权限与审计 |
| 线索从 CC 交接给 TMK | 业务流程 | 规则状态、权限审计 |
| 推荐好友获得会员奖励 | 业务流程 | 规则状态、用户端体验、看板指标 |
| 导入外部广告线索 | 集成与自动化 | 表单字段、规则状态 |
| 新增销售经营日报 | 看板与指标 | 权限审计 |
| 新增角色并限制敏感导出 | 权限与审计 | 表单字段列表 |
