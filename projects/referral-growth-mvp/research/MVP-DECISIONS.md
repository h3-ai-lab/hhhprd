# 拉新裂变 MVP 重构说明

## 从完整方案收敛到什么

上一版 `Referrals & Rewards` 同时包含用户端邀请、推荐码、试听奖励、购买奖励、社群审核、退款冲正、CRM 页面、告警和完整看板。私聊确认当前业务已经开始手工执行，真正痛点集中在两处：

1. CC 已经给推荐人加过会员，但没有结构化记录推荐关系和操作来源。
2. 忘记手写 referral 备注后，无法回答哪个 CC 操作、哪个推荐人贡献、带来了多少被推荐人和 GMV。

MVP 因此拆成“先绑定、后自动发奖”两段：

```text
CC 通知推荐人 → 推荐人邀请好友注册 → 好友将用户 ID 告知推荐人
→ 目标归属 CC 按用户 ID 校验新注册和推荐唯一性
→ 绑定成功并提示被推荐人的当前归属 CC
→ 当前归属 CC 使用重新分配线索转给目标归属 CC
→ 被推荐人首课完课、首次购买或产生其他奖励事件
→ 系统按事件枚举和规则生成奖励
→ 生成零金额赠送订单
→ 订单驱动权益服务开通会员
→ 看板自动出数
```

## 为什么绑定与发奖分离

- 关系应在业务事件触发前生效，并等待原归属 CC 完成线索重新分配。
- 首课完课、首次购买和 CC 登记的社群上传审核结果是彼此独立的后置事件，不能由绑定动作直接发放。
- 社群上传沿用 CC 在 CRM 代用户录入内容与凭证的操作，不新增 App 用户投稿入口。
- 绑定和发奖拆开后可分别幂等、分别审计，也避免 CC 手工计算奖励。
- 关系关联使用用户 ID，不使用手机号；被推荐人完成正式注册后才能绑定。
- 新注册以活动开始时间和被推荐人正式注册时间比较，活动前已有账号的用户不符合资格。
- 绑定不直接改写线索归属；必须由当前 CC 使用“重新分配线索”完成转移。

## 为什么不把“人工确认”全部去掉

推荐人与被推荐人的关系在当前 MVP 中没有客户端数据来源，必须由了解通话和推荐过程的 CC 录入。本期去掉的是：

- 在订单中心人工搜索并判断被推荐人是否支付。
- 人工判断套餐对应奖励。
- 发放后手写 referral 备注。
- 再由主管二次确认。

CC 的一次绑定提交只确认关系，不确认权益。

## 现状依据

- 当前“添加会员”弹窗提供“添加体验天数 / 手动银行转账”、有效期天数和开通原因。
- 用户中心以用户 ID 作为跨用户、订单和线索核对的主要标识。
- 订单中心支持按用户 ID 查看会员订单和支付状态。
- 现有销售中心保留已付费用户，可直接作为后续处理上下文。
- 推荐人从被推荐人处获取用户 ID 后提供给目标归属 CC，因此关系直接使用用户 ID 精确关联。
- 新注册判定以活动开始时间为起点，活动前已有正式账号的用户不纳入本次拉新奖励。
- 现有添加会员通过会员天数、`sourceType` 和唯一 `sourceBizKey` 更新会员权益；自动奖励复用其订单创建、权益联动和幂等逻辑，而不是直接改到期时间。
- 现有 CC 手工添加会员限制为 1～3 天；自动奖励由系统发放，需走系统授权入口，不受该人工额度限制。
- 现有手工添加会在用户存在有效商店订阅时被拦截；自动推荐奖励需要后端提供系统赠送白名单能力，并由权益服务最终确认结果。
