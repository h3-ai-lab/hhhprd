# 拉新裂变 MVP 重构说明

## 从完整方案收敛到什么

上一版 `Referrals & Rewards` 同时包含 C 端邀请、推荐码、试听奖励、购买奖励、社媒审核、退款冲正、CRM 页面、告警和完整看板。私聊确认当前业务已经开始手工执行，真正痛点集中在两处：

1. CC 已经给 B 加过会员，但没有结构化记录 B → C 关系和操作来源。
2. 忘记手写 referral 备注后，无法回答哪个 CC 操作、哪个 B 推荐、带来了多少被推荐人和 GMV。

MVP 因此拆成“先绑定、后自动发奖”两段：

```text
CC 联系 B → CC 录入 C 手机号并建立绑定
→ C 未注册时保存待注册预绑定
→ C 注册、首课完课或首次购买
→ 系统按事件枚举和规则生成奖励
→ 生成零金额赠送订单
→ 订单驱动权益服务开通会员
→ 看板自动出数
```

## 为什么绑定与发奖分离

- 关系需要在 C 注册前或购买前生效，才能参与线索分配保护。
- 首课完课、首次购买和社媒状态是彼此独立的后置事件，不能由绑定动作直接发放。
- 绑定和发奖拆开后可分别幂等、分别审计，也避免 CC 手工计算奖励。
- C 尚未注册时可以先按手机号预绑定，注册后自动补写用户 ID 和推荐归属。

## 为什么不把“人工确认”全部去掉

C 与 B 的关系在当前 MVP 中没有客户端数据来源，必须由了解通话和推荐过程的 CC 录入。本期去掉的是：

- 在订单中心人工搜索并判断 C 是否支付。
- 人工判断套餐对应奖励。
- 发放后手写 referral 备注。
- 再由主管二次确认。

CC 的一次绑定提交只确认关系，不确认权益。

## 现状依据

- 当前“添加会员”弹窗提供“添加体验天数 / 手动银行转账”、有效期天数和开通原因。
- 用户中心以用户 ID 作为跨用户、订单和线索核对的主要标识。
- 订单中心支持按用户 ID 查看会员订单和支付状态。
- 现有销售中心保留已付费用户，可直接作为推荐人 C 的后续处理上下文。
- CC 更习惯持有并输入客户手机号，因此 MVP 输入改为手机号；用户 ID 仍作为匹配后的内部唯一标识和关联合键。
- 手机号可能存在于多个业务线，匹配时必须使用推荐人当前所属业务线收窄范围，避免跨业务线误绑定。
- 现有添加会员通过会员天数、`sourceType` 和唯一 `sourceBizKey` 更新会员权益；自动奖励复用其订单创建、权益联动和幂等逻辑，而不是直接改到期时间。
- 现有 CC 手工添加会员限制为 1～3 天；自动奖励由系统发放，需走系统授权入口，不受该人工额度限制。
- 现有手工添加会在用户存在有效商店订阅时被拦截；自动推荐奖励需要后端提供系统赠送白名单能力，并由权益服务最终确认结果。
