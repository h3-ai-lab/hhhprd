# 拉新裂变 MVP Memory

## Confirmed Facts

- 当前手工链路为 CC 联系推荐人 B，B 线下邀请 C，C 在 App 购买套餐后，CC 在 CRM 给 B 增加免费会员并手写 referral 备注。
- 业务希望去掉单独人工确认；当前 CRM 已经可以手工加会员，单纯增加一个确认步骤没有价值。
- MVP 阶段 B 与 C 的关系仍由 CC 在 CRM 录入；C 端邀请链接和自动绑定放到第二版。
- 首版需要识别 referral / social post 来源，并能看到操作 CC、推荐人、被推荐人、人数和 GMV。
- 现有“添加会员”弹窗包含开通类型、有效期天数、开通原因和确认操作。

## Decisions

- 复用现有“添加会员”入口，不新建独立推荐审批流程。
- CC 在给 B 发放权益时录入 C 手机号，一次提交同时完成账号匹配、关系绑定和权益发放。
- 被推荐人手机号必须以推荐人 B 所属业务线为匹配范围；同业务线唯一命中才可继续。
- 系统自动核验 C 的有效付费会员订单，并带出推荐奖励；CC 不再手工判断订单和奖励时长。
- 一个被推荐用户只能绑定一个推荐人；同一对 B/C 只能存在一条有效关系。
- 推荐人 B 可以有多个被推荐用户。
- 本版仅支持好友购买 3/6/12 个月后的推荐奖励，分别是 +1/+2/+3 个月；首次试听 +14 天放到后续自动事件版本。
- 社媒分享首版记录用户、CC、内容链接和权益，不新增内容审核队列。
- 看板默认按关系绑定时间统计，也可切换归因订单支付时间；GMV 使用每条关系对应的唯一归因订单。
- 缺失的历史推荐关系不通过备注或行为猜测回补。

## Glossary

- 推荐人 B：接受 CC 活动沟通并向朋友推荐产品的现有用户。
- 被推荐人 C：由 B 推荐、手机号与推荐人同业务线唯一匹配，并完成有效付费会员购买的注册用户。
- 归因订单：每条推荐关系唯一关联的、用于判定推荐奖励和计算 GMV 的有效付费会员订单。
- 操作 CC：实际提交本次权益和关系记录的 CRM 账号。
- 归属 CC：本次拉新业绩计入的 CC，默认取推荐人当前线索负责人，允许有权限的管理者调整。
