## MVP 结论

CC 不进入新的审批队列，而是先维护关系：

1. 被推荐人完成注册并将用户 ID 告知推荐人，推荐人再将用户 ID 告知目标归属 CC。
2. 目标归属 CC 按用户 ID 核验被推荐人的业务线、正式用户状态、新注册和已有推荐关系。
3. 绑定成功后展示被推荐人的当前归属 CC；当前归属 CC 通过销售中心“重新分配线索”将其转给目标归属 CC。
4. 关系生效后，首课完课、首次购买或社媒推荐审核结果生成零金额赠送订单并驱动权益开通。

销售中心和用户列表都可发起关系维护；营销中心的指标、关系、奖励事件和赠送订单合并为同一个列表。

## 本版边界

- 用户端自动生成邀请链接和自动绑定放到后续版本。
- 首版支持首课完课与首次购买事件自动发奖。
- 社媒推荐由 CC 代用户登记用户、课堂、平台、内容凭证和授权，不建设 App 用户自助投稿，也不自动抓取第三方平台结果。
- 不回补无法核实的既有手工推荐，不通过备注猜测历史关系。
- 被推荐人只按用户 ID 精确关联；必须在活动开始后完成正式注册，且没有其他有效推荐关系。
- 所有业务校验前置；“发放失败”只记录校验通过后的权益服务或系统异常。
- 赠送订单沿用现有添加会员的订单、权益联动和来源业务键幂等机制，金额为 0，不计入 GMV 或付费用户。

## 交付节奏

| 阶段 | 产出 | 预计工作日 |
|---|---|---:|
| D1 | 需求与奖励规则确认、现有接口和权限盘点 | 1 |
| D2-D4 | 用户 ID 绑定、新注册校验、当前 CC 提示和归属转移 | 3 |
| D3-D5 | 好友推荐、CC 登记社媒推荐、审核和异常反馈页面 | 3 |
| D5-D7 | 首课、购买、社媒推荐结果与自动权益发放 | 3 |
| D7-D8 | 拉新看板、奖励事件和 CC 维度 | 2 |
| D9-D10 | 联调、灰度和上线核对 | 2 |

前后端可并行，按 10 个工作日排期。前提是复用注册、课程、订单和权益服务能力；若注册或课程服务需要新增事件，排期需单独评估。
