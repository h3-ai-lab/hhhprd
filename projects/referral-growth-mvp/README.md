## MVP 结论

CC 不进入新的审批队列，而是在给推荐人 B 添加会员时：

1. 选择“拉新推荐”或“社媒分享”来源。
2. 推荐场景录入被推荐人 C 的手机号。
3. 系统按推荐人所属业务线匹配唯一 C 账号，并核验注册状态和有效支付订单。
4. 系统自动带出奖励规则；CC 一次确认后同时写入 B → C 关系并发放 B 的权益。

推荐关系由这笔带来源的权益记录承载，不再让 CC 手写 `referral` 备注，也不再单独做一次人工确认。

## 本版边界

- C 端自动生成邀请链接和自动绑定放到后续版本。
- 首版聚焦好友购买后的推荐奖励，不自动监听首次试听事件。
- 社媒分享首版只做来源、内容链接、CC 和权益留痕，不建设内容审核队列。
- 不回补无法核实的既有手工推荐，不通过备注猜测历史关系。
- 被推荐人手机号只按精确值匹配推荐人同业务线账号；跨业务线或同业务线多账号匹配均阻止提交。

## 交付节奏

| 阶段 | 产出 | 预计工作日 |
|---|---|---:|
| D1 | 需求与奖励规则确认、现有接口和权限盘点 | 1 |
| D2-D4 | 权益记录、推荐关系、订单核验和幂等 | 3 |
| D3-D5 | 添加会员弹窗、推荐关系核验和异常反馈 | 3 |
| D5-D6 | 拉新看板、详情和 CC 维度 | 2 |
| D7-D8 | 联调、灰度和上线核对 | 2 |

前后端可并行，按 8 个工作日排期。前提是复用现有添加会员权益服务和订单查询能力；若任一方需要新增基础接口，排期需单独评估。
