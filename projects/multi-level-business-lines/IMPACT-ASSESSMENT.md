# 多级业务线：影响评估

> 结论：这是一次数据权限底座升级，不是系统配置页的单点改造。线索、用户、订单、通话、看板、搜索、导入和导出只要能看到客户数据，都必须接入同一套组织范围，否则会从其他入口绕过销售中心隔离。

## 1. 影响总览

| 模块 | 主要影响 | 优先级 | 风险等级 |
|---|---|---|---|
| 系统配置 | 新增组织树；成员归属和授权改为唯一数据范围来源 | P0 | 高 |
| 角色权限 | 角色只保留功能权限；移除角色级业务线数据范围 | P0 | 高 |
| 成员账号 | 增加业务线内主归属和逐业务线数据授权 | P0 | 高 |
| 数据分组 | 升级为组织节点或明确下线，避免双轨团队模型 | P0 | 高 |
| 销售中心 | 公海、我的跟进、已付费、通话记录的可见范围改为组织范围 | P0 | 高 |
| 分配与掉库 | 候选人、权重、退还和重新分配受组织归属约束 | P0 | 高 |
| TMK 与转交 | TMK 手动转交目标限定在同一业务线及合法节点范围 | P0 | 中 |
| 用户中心 | 用户详情及关联线索、订单不可越权查看 | P0 | 高 |
| 订单中心 | 订单按业务归属、负责人和关联线索控制 | P0 | 高 |
| 管理看板 | 汇总、筛选候选、下钻、导出统一按组织子树计算 | P0 | 高 |
| 营销配置 | 渠道、SKU、落地页等配置仍以业务线为主；节点管理者不应自动获得整线配置权 | P1 | 中 |
| 导入与下载 | 批量能力按同一范围鉴权，导出需独立权限和审计 | P0 | 高 |
| 操作日志 | 组织调整、授权、调组、转派和导出必须可追溯 | P0 | 高 |
| 数仓/BI | 需要可用的业务线和当前组织节点归属，不能继续依赖权限标签 | P1 | 高 |
| 在建需求 | 二级团队、TMK、首位 CC、团队监控依赖的数据范围需要统一 | 立即协调 | 高 |

## 2. 逐模块影响

### 2.1 系统配置

现有系统配置包含角色权限、成员账号、操作日志，较新的方案还包含数据分组。目标应新增“组织架构”能力，并明确数据分组的迁移或下线节奏。

页面影响：

- 组织树支持新建、重命名、更换上级、停用、合并和空节点删除。
- 成员账号增加每个业务线的主归属组织。
- 成员账号增加数据授权区，展示业务线、范围类型和授权节点。
- 编辑成员时展示“归属组织 + 功能角色 + 数据范围”三组信息，不能只展示角色。
- 组织调整前展示受影响成员、线索、规则和看板数量。

系统风险：

- 若组织树和数据分组同时保留，用户会配置两套团队，权限结果不可解释。
- 若组织负责人自动获得节点范围，历史负责人变更会静默扩大权限。
- 若删除节点允许带走历史数据，审计和历史统计会断裂。

### 2.2 角色权限

现有文档同时存在两种描述：角色配置数据范围，以及角色只管功能、成员账号配置数据范围。目标必须只保留后者。

目标：

- 角色定义菜单、页面、查看、编辑、转派、配置、导入、导出、字段脱敏等动作。
- 数据范围只在成员授权中配置。
- 同名或同岗位角色不自动映射为数据范围。
- 角色修改影响功能能力，不应无声改变所有成员的数据边界。

迁移风险：若存量角色上仍有有效业务线范围，必须按上线前实际权限导出并映射，不能简单删除角色范围后让成员失去访问，也不能默认给成员更大范围。

### 2.3 成员账号

成员账号将成为权限解释中心。至少需要表达：

- 账号状态。
- 功能角色。
- 每个业务线的主归属组织。
- 每个业务线的数据范围：本人、节点及下级、本业务线全部。
- 节点范围下所选节点。
- 生效时间和变更记录。

影响：

- 没有主归属的在职销售不能接收新线索。
- 跨业务线成员需要逐线配置，不能用一个全局范围代替。
- 编辑、停用、调组和授权变更必须即时影响下一次请求。
- 候选人、负责人、筛选器等需要按成员是否有效及是否在同一业务线筛选。

### 2.4 数据分组与组织树

现有数据分组是单层团队模型，多级业务线需要树结构。若直接把“分组”改名为“组织”，但数据模型仍是平面列表，会遇到同类问题。

建议：

- 将数据分组升级为组织节点，保留稳定 ID。
- 旧分组成为业务线根节点下的节点。
- 成员“所属组”迁移为“主归属组织”。
- “指定组数据”迁移为“节点及下级”。
- 分组负责人保留组织负责人记录。

如果两级团队版本尚未上线，应合并为一次组织树交付；如果已经上线，应先做兼容映射，避免同时存在两套团队数据。

### 2.5 销售中心

影响页面：

- 公海。
- 我的跟进。
- 已付费。
- 通话记录。
- 线索详情与分配历史。

影响动作：

- 查看和搜索。
- 领取。
- 自动分配。
- 重新分配。
- 退回公海。
- 掉库后重分配。
- 导入 leads。
- 下载数据。

规则：

- 普通成员按本人范围查看。
- 节点管理者可看授权子树内线索，但不能看兄弟节点。
- 业务线负责人可看该线全部线索。
- 跨节点转派只允许对源线索有编辑/转派权限且目标成员在合法业务线或有明确跨节点转派权限的操作者执行。
- 搜索、筛选候选和直链详情必须与列表同权限。
- 公共池线索必须有一个组织归属，否则节点管理者看不到，业务线管理者可能看到但无法按团队运营。

### 2.6 分配与掉库

影响：

- 自动分配的候选集合从“业务线成员”变为“业务线 + 有效主归属 + 数据/功能资格 + 权重 + 休息日”的交集。
- 节点管理者只能维护授权节点中成员的权重、休息日和候选，不自动获得修改整条业务线规则的权限。
- 线索掉库或退回后，需要决定回到原节点公共池还是业务线公共池。
- 线索重新分配时应同步更新当前归属组织。
- 同一个人不能在多个节点中因兼任而重复增加分配权重。

主要风险：只限制列表可见，却仍把线索自动分配给无主归属人员，会造成“系统分配成功但负责人和团队都看不到”的断链。

### 2.7 TMK 与手动转交

结合现有 TMK 方案：

- TMK 预约后手动转交 CC。
- CC 候选项限定为同业务线、启用、有跟进能力并有有效主归属的人员。
- 默认只能选择操作人数据范围内的 CC。
- 跨节点转交需要更高的转派权限，并记录原因、源节点和目标节点。
- 转交成功后线索当前组织节点同步为目标 CC 的主归属。
- 未转交时线索仍归 TMK 所属节点，按 TMK 自身数据范围查看。

### 2.8 用户中心

用户中心容易成为权限绕过入口。影响包括：

- 用户详情中的线索、订单、通话和学习信息必须按具体关系过滤。
- 搜索候选和用户列表不能展示无权节点中的手机号、用户 ID 或完整资料。
- 已付费用户可能跨多个业务线或订单；只展示与当前有权业务归属相关的部分。
- 用户导出与用户列表使用相同范围。

如果只隔离销售中心而不隔离用户中心，二级管理者仍可通过用户搜索查看兄弟团队客户。

### 2.9 订单中心

订单必须能解释其业务归属：

- 业务线。
- 关联线索或用户。
- 当前销售负责人。
- 订单当前归属组织。

订单列表、详情、退款/续费记录、导出按同一范围执行。跨业务线用户的历史订单不能因为共享用户账号而全部暴露。

### 2.10 管理看板

影响：

- 组织筛选候选只展示有权节点。
- 父节点汇总包含所有下级，但同一线索或用户只计算一次。
- 跨业务线汇总需要多条业务线授权；只有单条业务线“全部”时不能看到其他业务线。
- 汇总数字、下钻明细、排序和导出使用同一时间、业务线和组织范围。
- 组织调整后，历史指标是按事件发生时的归属统计还是按当前归属重算，必须统一口径。

推荐：经营结果遵循业务发生时的归属快照，当前存量运营视图按当前归属展示，并在看板中明确当前/历史口径。

### 2.11 营销中心与业务配置

渠道、SKU、价格、落地页和皮肤仍以业务线为配置边界。

- 节点管理者不应仅因有节点数据范围就修改整条业务线配置。
- 修改业务线整体分配规则、渠道、价格等配置，需要业务线全部数据范围和对应功能权限。
- 节点范围可以用于查看与该节点相关的线索来源或经营数据，但不自动扩大配置编辑权。

### 2.12 导入、导出与外部共享

- 导入 leads 时，业务线和默认归属节点是必填业务语义；无有效组织的行不应静默进入公共池。
- 导入历史负责人时，只更新当前事实，不据此改写首跟 CC 等历史事实。
- 导出使用当前列表筛选、排序和数据范围，不能先导出再按页面隐藏。
- 导出文件生成后，用户权限撤销不影响历史文件，但再次下载和重新生成必须重新鉴权。
- 外部分享链接、接口和开放能力不能绕开节点权限。

### 2.13 操作日志与审计

新增审计对象：

- 组织节点创建、改名、换上级、停用、合并和删除。
- 成员归属和角色变化。
- 数据授权新增、修改和撤销。
- 人员调组后线索交接。
- 跨节点或跨业务线转派。
- 批量领取、批量转派和导出。
- 越权访问尝试。

审计至少包含操作人、时间、对象、动作、变更前、变更后、原因、来源和生效时间。组织调整和授权变更不允许普通管理员直接删除历史。

### 2.14 数仓与 BI

权限标签不能继续作为唯一组织来源。下游至少需要获得：

- 业务线根节点。
- 线索当前组织节点。
- 线索负责人。
- 组织节点父子关系及有效期。
- 成员归属及有效期。

若 BI 直接展示明细或允许自助下载，必须与 CRM 使用相同权限口径；否则会成为另一个越权入口。

## 3. 对现有功能和在建需求的衔接

| 现有能力/需求 | 影响 | 处理建议 |
|---|---|---|
| 业务线 + 数据范围 | 可复用范围枚举，但数据分组需升级为组织树 | 合并设计 |
| 数据分组页签 | 将成为组织节点管理，避免双轨 | 先做迁移映射 |
| TMK 分配与手动转交 | CC 候选必须加组织归属约束 | 与组织树同批 |
| 首位 CC 与团队监控 | “团队范围”需明确为组织节点子树 | 更新数据范围定义 |
| 销售中心筛选 | 国家/业务线之外的组织筛选受数据授权限制 | 与权限同步上线 |
| 管理看板 | 组织树汇总和下钻需要统一口径 | P0 后置会形成绕过 |
| 分配与掉库设置 | 业务线规则与节点成员配置权限分离 | 同步调整 |
| 用户中心/订单中心导出 | 需要同范围鉴权 | 不能晚于销售中心 |

现有需求文档中的角色默认授权示例使用“所属团队 + 所属业务线”。该表达不够精确，正式 PRD 应改为“该成员在业务线内被显式授权的组织节点及下级”，避免把归属组织自动当成数据范围。

## 4. 高风险场景

| 风险 | 典型后果 | 控制方向 |
|---|---|---|
| 只在销售中心加权限 | 通过用户搜索、订单、通话或导出看到兄弟团队数据 | 全客户数据入口统一范围 |
| 组织负责人自动授权 | 头衔变化导致数据意外扩大 | 归属、授权、负责人解耦 |
| 角色和成员同时配置范围 | 两个管理员看到不同结果，无法解释 | 唯一数据范围来源 |
| 调组自动迁移线索 | 客户责任和业绩被静默改变 | 明确交接 |
| 节点删除后重建 | 历史归属变成未知，权限被新节点继承 | 禁止删除有历史节点 |
| 组织移动不提示 | 子树上百人可见范围瞬间变化 | 影响预览和审计 |
| 无组织成员参与自动分配 | 分配成功但团队不可运营 | 候选资格包含有效主归属 |
| 权限标签继续参与鉴权 | 两套规则冲突并留下后门 | 标签退出安全边界 |
| 导出先查全量再截断 | 用户获得无权数据 | 查询和导出同权限 |

## 5. 实施顺序建议

```mermaid
flowchart LR
    A[冻结权限语义] --> B[组织树与成员归属]
    B --> C[存量组织与授权迁移]
    C --> D[线索当前组织归属]
    D --> E[销售中心与候选权限]
    E --> F[用户 订单 通话]
    F --> G[看板 下钻 导出]
    G --> H[单业务线灰度]
    H --> I[全量切换并停止标签鉴权]
```

### P0

- 业务线根组织、二级及以下节点。
- 成员主归属和三类数据范围。
- 角色功能权限与数据范围解耦。
- 存量分组、成员和权限迁移。
- 线索当前组织归属及分配生命周期更新。
- 销售中心、用户、订单、通话和公共池统一权限。
- 看板汇总、下钻和导出统一权限。
- 审计、调组待交接和影响预览。

### P1

- 更完善的组织合并和批量交接工具。
- 外部 HR 组织同步。
- 自定义组织视图、跨业务线矩阵授权。
- 权限解释器和更细的授权有效期。

## 6. 上线判断

只有同时满足以下条件，才应移除旧标签鉴权：

1. 真实账号在只读影子校验中的新旧可见范围差异已全部解释。
2. 每条在职销售都有有效主归属组织。
3. 公共池、无负责人和停用人员的存量线索有明确运营归属。
4. 列表、详情、搜索、候选人、看板、下钻和导出均使用同一权限口径。
5. 组织调整、人员调组和授权撤销可即时生效并可追溯。
6. 已确认本次上线不是“销售中心局部隔离”，而是客户数据访问边界的统一升级。
