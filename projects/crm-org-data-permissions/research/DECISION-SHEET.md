# 多级业务线：决策清单

> 本文用于项目启动和业务评审。未确认项不写入正式 PRD；下列推荐值可先作为讨论基线。

## 1. 已确认方向

| ID | 决策 | 状态 |
|---|---|---|
| C-01 | 不再用多级权限标签作为主要隔离方案 | 已确认 |
| C-02 | 通过 CRM 账号的组织归属和组织树解决多级数据权限 | 已确认 |
| C-03 | 数据范围包含全部、节点及下级、本人三种 | 已确认方向，具体口径待冻结 |
| C-04 | 同一业务线内，一个人只能配置一个功能角色、一条数据授权和一个行政主组织节点 | 已确认 |
| C-05 | 一条数据授权可以包含 A+B 多个节点，只决定可操作数据，不改变行政主组织 | 已确认 |
| C-06 | 业务数据按发生时点的组织节点记录完整路径；人员或组织变化只影响之后产生的数据，不回写历史 | 已确认 |
| C-07 | 组织最多四层：国家、区、部、组；任意层级都可直接承接业务，不强制数据落到最末级 | 已确认 |

## 2. 建议冻结项

| ID | 决策项 | 推荐结论 | 为什么 |
|---|---|---|---|
| R-01 | 业务线是否作为组织树根节点 | 是；业务线根节点下承载二级和更深组织 | 保留业务线作为时区、分配、看板的主边界 |
| R-02 | “全部”的含义 | 默认指所选业务线全部；另设独立全局权限 | 防止授权越南时意外看到其他业务线 |
| R-03 | 节点范围是否自动包含全部下级 | 是，父节点包含所有下级，不包含父级和兄弟节点 | 避免每新增下级都补权限规则 |
| R-04 | 成员在同一业务线是否可属于多个主组织 | 建议每个业务线只有一个主归属；兼任通过数据授权表达 | 避免分配权重、负责人和候选项重复 |
| R-05 | 归属组织是否自动授予数据范围 | 否 | 防止调组或任命负责人时静默扩大权限 |
| R-06 | 组织负责人是否自动获得管理能力 | 否 | 负责人是记录角色，数据和动作权限需单独配置 |
| R-07 | 人员调组后已有线索如何处理 | 保持原归属并进入待交接，不自动批量迁移 | 保护客户责任、业绩和历史可见性 |
| R-08 | 新线索的归属节点如何确定 | 有明确来源时归属来源目标组织；直接分给个人时归属接收人的行政主组织 | 保持唯一归属且不需要额外作业组织配置 |
| R-09 | 线索退回公海后的组织归属 | 回到明确的业务线待分配节点或配置的节点公共池 | 无主归属的公共线索仍需可运营 |
| R-10 | 是否允许跨业务线转派 | 默认禁止；如业务需要，仅高权限显式操作并审计 | 避免客户责任跨业务线静默变化 |
| R-11 | 谁是数据范围唯一配置来源 | 成员账号中的数据授权 | 消除角色与成员双重配置 |
| R-12 | 迁移时无法确认的授权如何处理 | 不扩大权限，进入人工确认 | 安全默认拒绝 |
| R-13 | 是否继续并保留数据分组 | 升级为组织节点；不长期双轨 | 两套团队模型会导致解释和迁移冲突 |
| R-14 | 对象范围 | 所有直接或间接触达客户数据的能力 | 只改销售中心会形成越权入口 |
| R-15 | 成员同时属于 A、B 时，分配给其线索的归属节点 | 线索只保留一个运营归属节点；由分配来源组织决定，主归属仅作无来源规则时的默认值 | 防止同一线索同时进入两个团队、被重复统计或出现双负责人 |
| R-16 | A、B 双团队是否需要共同跟进同一线索 | 默认由归属组织负责；共同跟进作为显式协作关系，不复制第二条归属 | 协作需求和数据归属必须分开 |
| R-17 | 是否要求管理者在每次作业时选择生产组织 | 否；外呼、跟进和成交继承线索当前归属，避免重复选择和组织不一致 | 降低配置与操作复杂度 |
| R-18 | 父组织直属业务如何进入汇总 | 保留“区直属/组织直属”数据桶，父节点汇总包含直属与全部下级 | 保证区汇总和 A/B 部门之和能够核对 |
| R-19 | 跨组织共同贡献的首期处理 | 不做业绩分摊，严格按线索成交时的运营归属组织统计 | 保持组织归属与业绩口径一致 |
| R-20 | 过程看板按当前组织还是历史组织统计 | 按事件发生时组织快照；当前存量列表按当前组织 | 避免人员调组或线索转派后历史数字自动变化 |
| R-21 | 看板与明细是否使用同一范围 | 是；下钻和导出继续校验明细数据权限 | 防止从汇总入口绕过隔离 |
| R-22 | 一级业务线存量数据是否统一倒推到新组织 | 否；仅用可靠证据映射，未结线索可用迁移时组织，已结束历史保留原业务线口径 | 防止伪造历史归属和历史数字漂移 |
| R-23 | 存量账号尚未配置组织时如何处理 | 允许查看已有授权，补齐组织前不接收新线索；无法映射的账号进入待归属节点 | 保证新业务不再产生无组织归属数据 |

## 3. 启动前必须确认

以下四项会改变产品结构，建议进入开发前逐项签字冻结：

| ID | 必须确认的问题 | 当前推荐 | 影响 |
|---|---|---|---|
| D-01 | 业务线根、组织节点、子业务线是否采用同一棵树 | 同一棵树，业务线为根 | 决定配置页、数据对象和看板维度 |
| D-02 | “全部”到底指业务线全部还是公司全部 | 业务线全部；公司全局另设权限 | 决定是否会出现跨线数据泄露 |
| D-03 | 人员调组时已有客户是否随人迁移 | 不随人自动迁移，显式交接 | 决定销售责任、业绩和历史权限 |
| D-04 | 跨节点、跨业务线转派需要什么级别权限 | 跨业务线默认禁止；跨节点需显式权限和原因 | 决定销售流程与敏感操作审计 |

## 4. 第二批评审项

| ID | 决策项 | 推荐结论 |
|---|---|---|
| D-05 | 业务线内是否支持成员多归属 | 保留数据授权多节点，主归属只一个 |
| D-06 | 节点移动时权限是否立即生效 | 立即生效；保存前展示影响并要求原因 |
| D-07 | 节点停用后已有成员和线索是否可保留 | 保留；停止新增分配，要求限期处理 |
| D-08 | 组织合并是否支持撤销 | 支持在未产生新业务数据且有完整映射时回滚 |
| D-09 | 看板历史数据按事件归属还是当前归属 | 经营结果按业务发生时点，当前运营视图可明确标注当前归属 |
| D-10 | 是否首期接入外部 HR 组织 | 不接入，先由 CRM 管理员维护 |
| D-11 | 新线索接收人缺少主归属时如何处理 | 不参与自动分配；人工转派时阻止并提示补配置 |
| D-12 | 权限撤销是否影响已生成文件 | 已生成文件保留，后续下载和重新生成重新鉴权 |
| D-13 | 成员固定兼任 A、B 且长期接收两边的线索时，每次按哪个节点归属 | 按领取/分配规则触发节点；无法判断时要求操作人选择归属团队，不能默认同时归属 |
| D-14 | 线索的运营归属、来源归属和业绩归属是否允许不同 | 允许拆分记录，但默认三者一致；跨团队协助通过独立贡献或协作记录表达 |
| D-15 | 非最末级组织是否允许直接承接业务和产生业绩 | 建议允许；国家、区、部、组均可直接产生数据，不要求落到组 |
| D-16 | 区直属业绩是否需要在 A/B 中拆分 | 首期不拆分；直属业绩只在直属组织及上级汇总中出现 |
| D-17 | 过程看板是否统一使用事件时组织快照 | 建议统一，避免组织调整后历史经营数据变化 |
| D-18 | 已成交历史订单是否按当前负责人新组织重算部门归属 | 建议不重算；只保留原业务线、负责人和可验证的历史团队证据 |
| D-19 | 历史未映射数据是否需要限时只读兼容权限 | 建议需要，范围仅限切换前数据，并设置结束时间 |

## 5. 业务评审建议

建议用真实组织各举一组数据验证：

- 两个同级管理者只能看到各自子树。
- 上级管理者能看到所有下级，不看到兄弟业务线。
- 一线销售只看本人，不通过搜索、用户中心或导出看到更多。
- 两名管理者互相转派后，原管理者失去当前线索，接收管理者获得权限。
- 人员调组后，新旧团队在交接前后的可见性符合约定。
- 节点换上级后，可见范围即时变化且审计记录可解释。
- 跨业务线账号按业务线分别显示数据，不因“全部”扩散。

## 6. 正式 PRD 启动条件

以下条件全部满足后，再创建 `PRD.md` 和交互原型：

1. D-01 至 D-04 已由业务负责人确认。
2. 存量分组、角色范围、成员范围和线索标签的迁移口径可执行。
3. 已确认 P0 覆盖哪些客户数据入口。
4. 已确认组织负责人、分配权限和跨节点转派的边界。
5. 已在一条业务线选定试点组织和对照账号。

## 7. 下一步

1. 召开一次 60–90 分钟业务决策会，只讨论 D-01 至 D-04。
2. 获取一条真实业务线的最小组织样例、人员归属和现有权限清单。
3. 形成组织/账号/授权/线索归属的字段与页面路径，再开始正式 PRD。
4. 以一条业务线做新旧权限影子对照，验证无扩大、无遗漏后再安排全量。
